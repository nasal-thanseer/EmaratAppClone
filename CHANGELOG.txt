DATABASE AND RLS SECURITY
- Integrated the profiles, wallets, merchants, merchant_staff, transactions,
  redemption_tokens, and audit_logs data model.
- Enabled RLS-safe reads for members and merchant staff.
- Limited profile updates to the authenticated user's full name.
- Restricted merchant visibility to active merchants.
- Restricted transactions to the owning member or assigned merchant staff.
- Added the auth.users trigger that creates a profile and zero-balance wallet.
- Added atomic earn and redeem functions with authorization checks, row locks,
  idempotency handling, balance validation, and audit logging.
- Revoked anonymous execution from all privileged functions.
- Allowed authenticated execution only for the three intended mobile RPCs:
  create_redemption_token, earn_points, and redeem_token.
- Removed client execution access from internal trigger and helper functions.
- Optimized RLS policies to evaluate auth.uid() once per statement.
- Added indexes for merchant assignments, redemption-token relationships, and
  transaction member/merchant lookups.
- Ran Supabase security and performance advisors after database hardening.
- Left audit_logs intentionally inaccessible to mobile clients.

- Added a migration reproducing the live signup and pgcrypto fix.
- Improved messages for invalid email addresses and database-side account
  setup failures.

- Added a dedicated /auth/callback route that securely exchanges Supabase PKCE
